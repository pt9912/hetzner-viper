# Hetzner Viper

[English](README.md) | **Deutsch**

**VIPER** steht für **VI**rtual **PER**son: ein Code-Agent, der wie eine weitere Person im Team auf einem eigenen Rechner in Ihrem Repository arbeitet.

## Was ist Hetzner Viper?

Ein einzelnes Programm, `viper`, das mit einem Befehl einen entfernten Linux-Rechner bei einem Cloud-Anbieter (Hetzner Cloud, AWS, Google Cloud oder Azure), als Pod in einem Kubernetes-Cluster oder als Container auf dem eigenen Docker-Host einrichtet. Auf diesem Rechner arbeitet der Code-Agent [Claude Code](https://github.com/anthropics/claude-code) remote in Ihrem Repository: Er liest und ändert Code, führt Builds und Tests aus und committet. Pro Git-Repository gibt es einen eigenen Rechner. Das Repository wird beim Einrichten automatisch geklont. Sie steuern den Agenten per SSH, VS Code Remote-SSH oder vom iPad, in einer tmux-Sitzung, die Verbindungsabbrüche übersteht. Wer fertig ist, löscht den Rechner wieder, und es entstehen keine laufenden Kosten.

Zielgruppe sind Entwicklerinnen und Entwickler mit eigenem Cloud-Konto oder eigenem Cluster: **Hetzner Cloud** (Standard), **AWS** (`PROVIDER=aws`, Amazon EC2) ein **Kubernetes-Cluster** (`PROVIDER=kubernetes`, in k3d getestet) oder der **Docker-Host Ihres eigenen Computers** (`PROVIDER=compose`, ohne Cloud-Konto und ohne Cluster). Google Cloud und Azure (`PROVIDER=gcp`, `azure`) gibt es, sie sind aber nur gegen nachgebildete Schnittstellen getestet; ein Lauf in einem echten Konto ist nicht belegt. Der DNS-Name der Rechner kommt aus einer Cloudflare-Zone; ohne Cloudflare und ohne Domain (`DNS_PROVIDER=none`) erreichen Sie einen Rechner über seine Adresse (einen Pod oder Container erreicht `viper` immer über die API seines Hosts).

## Was kann ich heute tun?

`viper` ist eine Datei (Linux, macOS und für Windows `windows_amd64.exe`, das nur teilweise getestet ist: `viper` in WSL mit dem Linux-Binary ist zuverlässiger) von der [Releases-Seite](https://github.com/pt9912/hetzner-viper/releases) oder mit Homebrew: `brew install pt9912/viper/viper`. Es braucht den OpenSSH-Client (`ssh`, `ssh-keygen`, `ssh-keyscan`, `scp`) und sonst nichts: kein `make`, `hcloud` oder `jq` (`git` dient der Repository-Prüfung und `code` dem Öffnen von VS Code, beides optional). Docker braucht nur, wer das Image für Pods baut (`viper image build`).

```bash
mkdir ~/viper && cd ~/viper        # hier liegt Ihre .env.local
viper find --cpu 4 --ram 16 --disk 80   # welcher Servertyp passt, bei welchem Anbieter, für wie viel (nur lesend, ohne Rechner)
viper setup                        # legt .env.local aus einer Vorlage an; DNS_DOMAIN (oder DNS_PROVIDER=none) und Zugangsdaten eintragen, dann erneut:
viper setup                        # Login-Key und lokale Host-CA anlegen
viper preflight web                # nur lesende Prüfung: Einstellungen, Cloud-Anbieter, Cloudflare, GitHub
viper up web --repo https://example.org/org/web.git   # Rechner "web" einrichten, Repo klonen
viper check web                    # nur lesend: DNS, Zugriff über den Namen wie ein anderes Gerät, Server-Zustand
viper ssh web                      # Shell auf dem Rechner (--cmd "..." für einen Befehl)
viper ssh web --tmux                # an die tmux-Sitzung "claude" anhängen (die von VS Code)
viper vscode web                   # VS Code erneut auf dem Rechner öffnen (wie viper up)
viper down web                     # auf ungesicherte Arbeit prüfen, dann Rechner "web" löschen
viper dns web                      # DNS-Name des Rechners "web" ausgeben
viper log [web] [--full]           # Ereignisse der Rechner oder die vollständige Ausgabe eines Rechners
viper ui                           # Rechner, Prüfen, Vorprüfung/Up/Down, NATS und Protokolle im Browser (nur 127.0.0.1)
viper up --group dev               # alle Rechner aus groups/dev.env gleichzeitig (ebenso down, check, preflight, ssh --cmd)
viper nats send dev "Bitte pushen" --to beta   # von diesem Rechner aus mit einer NATS-Gruppe sprechen (auch peers, listen, broadcast, request)
viper image build --k3d viper      # das Image der Rechner eines Kubernetes-Clusters (PROVIDER=kubernetes), in einen k3d-Cluster
viper mcp-binary --arch arm64 > f  # der eingebaute MCP-Server für NATS-Gruppen als Datei
```

| Funktion | Einstellung | Wirkung |
|---|---|---|
| Prüfung nur lesend | `viper preflight <name>` | Prüft vorab, bevor etwas angelegt wird: Einstellungen, lokales Setup, Cloud-Anmeldung (Hetzner-Token, AWS-Anmeldung, ...), Bestellbarkeit des Servertyps am Standort, Image, Cloudflare-Zone und -Eintrag, GitHub-Token und Repo-Zugriff. `viper up` führt es zuerst aus. Für eine Gruppe: `viper preflight --group <gruppe>`. |
| Anbieter | `PROVIDER=hetzner` (Standard), `aws`, `gcp`, `azure`, `kubernetes`, `compose` | Wo die Rechner laufen. Zugangsdaten, Servertyp, Standort und Image haben Standardwerte je Anbieter; Hetzner, AWS und Kubernetes (in k3d) sind erprobt, `gcp` und `azure` nur gegen nachgebildete Schnittstellen getestet (ein Lauf in einem echten Konto ist nicht belegt). |
| Pods in einem Kubernetes-Cluster | `PROVIDER=kubernetes`, `SERVER_LOCATION` (der Kontext), `K8S_IMAGE`, `K8S_*` | Ein Rechner ist ein Pod eines vorhandenen Clusters, mit einem Volume für das Heimverzeichnis und einem für Homebrew; er läuft ohne root. Das Image ist das veröffentlichte Ihrer `viper`-Version (`ghcr.io/pt9912/viper-machine`, amd64 und arm64), solange `K8S_IMAGE` kein anderes nennt; `viper image build [--k3d CLUSTER]` baut eines mit Docker aus Dateien, die in `viper` stecken. Mit `K3D_REGISTRY` (und `K3D_CLUSTER_CREATE=1`, `K3D_AGENTS`) legt `viper up` eine k3d-Registry an, bei Bedarf auch den Cluster, schiebt das Image hinein und lässt die Pods es von dort laden; `viper down` nimmt den Cluster, den es angelegt hat, mit dem letzten Rechner mit und fragt nach der Registry. Docker auf dem Rechner ist standardmäßig ein privilegierter Sidecar (`K8S_DOCKER`). Erreichbar über die API des Clusters, also ohne Adresse, DNS und Firewall. In k3d getestet, nicht in EKS, GKE oder AKS. |
| Container auf einem Docker-Host | `PROVIDER=compose`, `SERVER_LOCATION` (der Docker-Kontext), `COMPOSE_*` | Ein Rechner ist ein Container auf dem Docker-Host Ihres eigenen Computers, gestartet mit `docker compose` aus einer `compose.yaml`, die `viper up` schreibt (die Rechner einer Gruppe teilen ein Projekt und eine Datei, ein Rechner ohne Gruppe hat seine eigene); das Image ist das veröffentlichte Ihrer `viper`-Version, solange `COMPOSE_IMAGE` kein anderes nennt, und `viper up` lädt es, wenn der Host es nicht hat; mit einem Volume für das Heimverzeichnis und einem für Homebrew, ohne root. Docker auf dem Rechner ist standardmäßig ein privilegierter zweiter Container (`COMPOSE_DOCKER`). Erreichbar mit `docker exec`, also ohne Adresse, DNS und Firewall. NATS-Gruppen gehen (die Gruppe ist ein Docker-Netz). Auf einem lokalen Linux-Docker-Host getestet. |
| Ohne Cloudflare (optional) | `DNS_PROVIDER=none` | Kein DNS-Eintrag, keine Domain, kein Cloudflare-Konto: Ein Rechner ist mit `viper ssh <name>` oder über seine Adresse erreichbar (bei AWS zeigt `viper up` auch den Namen, den EC2 vergibt). |
| Eigene AWS-Tags (optional) | `AWS_TAGS`, `AWS_TAGS_SHARED` | Tags für Instanz und Systemplatte (`AWS_TAGS`) sowie für Schlüsselpaar und Security Group (`AWS_TAGS_SHARED`), gesetzt beim Anlegen, sodass auch Tag-Richtlinien (`aws:RequestTag`) den Start zulassen. Der Preflight prüft sie. |
| Mehrere Rechner | `viper up api …` neben `web` | Jeder Rechner hat eigenen Server und DNS-Namen `<SERVER_PREFIX>-<name>.<DNS_DOMAIN>` (Standard-Präfix `claude`). |
| Rechnergruppen | `groups/<gruppe>.env`, `viper up\|down\|check --group <gruppe>`, `viper ssh --group <gruppe> --cmd …` | Die Datei nennt die Rechner (`GROUP_MACHINES=alpha,beta`) und ihre gemeinsamen Einstellungen; ein Befehl startet, prüft oder löscht alle **gleichzeitig**, mit `[rechner]` vor jeder Zeile und einer Ergebnistabelle. Eine neue NATS-Gruppe bekommt zuerst ihren Server, die übrigen Rechner folgen währenddessen; `down` löscht zuerst die Clients, zuletzt den Server. Ein Rechner darf in mehreren Gruppen stehen; für einen einzelnen Rechner sagt `--in-group <gruppe>`, wessen Einstellungen gelten (`viper up web --in-group dev`). |
| NATS-Gruppen (optional) | `NATS_ENABLED`, `NATS_GROUP`, `NATS_PORT`, `NATS_OBJECTS`, `NATS_OBJECTS_MAX`, `NATS_OBJECTS_FILE_MAX`, `NATS_OBJECTS_TTL` | Die Rechner einer Gruppe sprechen über NATS in einem privaten Netzwerk miteinander: TLS, ein NKey je Rechner und Subjects, in die nur der Rechner selbst senden darf (der Absender einer Nachricht ist das Wort des Servers). Der erste Rechner wird der Server, die übrigen Clients; `viper down` widerruft den Schlüssel eines Clients. Bei Hetzner, in einem Kubernetes-Cluster (k3d) und mit Docker Compose ist es echt gelaufen; AWS, Google Cloud und Azure sind nur gegen nachgebildete Schnittstellen getestet. |
| Mit einer NATS-Gruppe sprechen (optional) | `viper nats peers\|topics\|listen\|send\|broadcast\|request\|fetch <gruppe>`, `viper nats init <gruppe>` | Liest und sendet Nachrichten einer Gruppe von Ihrem Rechner aus (`--file` nimmt einen langen Text aus einer Datei), als einer ihrer Rechner oder, nach `init`, als Betreiber mit eigenem Schlüssel (über einen SSH-Tunnel). `listen --all` zeigt auch die Direktnachrichten zwischen den anderen: In einer Gruppe ist nichts privat. Mit `NATS_OBJECTS=true` kann eine Nachricht ein Bild, ein PDF oder eine ZIP-Datei tragen (`--pdf`, `--image`, `--zip`; `viper nats fetch` holt sie): Die Datei liegt im Speicher des NATS-Servers der Gruppe, den jede Maschine der Gruppe lesen und auch leeren kann. |
| Oberfläche im Browser (optional) | `viper ui [--port N] [--no-open] [--readonly]` | Ein kleiner Webserver auf `127.0.0.1` im selben Programm, ohne zusätzliche Software: Ihre Rechner und Gruppen mit Zustand, `viper check`, `preflight`/`up`/`down` mit Ausgabe, Rückfragen und Abbrechen, die NATS-Gruppen (wer ist da, mitlesen, Text und Dateien senden, Datei holen) sowie Protokolle und Einstellungen (Werte nur bei Einstellungen, die keine Zugangsdaten sind). Deutsch oder Englisch. Nur Ihr Rechner erreicht sie, mit einem Schlüssel, der einmal gilt; die Ausgaben ersetzen die bekannten Zugangsdaten durch `[hidden]`. |
| Claude Code spricht mit anderen Rechnern (optional) | `NATS_MCP`, `NATS_MCP_PUSH_FROM`, `NATS_MCP_TOPICS`, `NATS_MCP_AUTOALLOW` | Installiert den MCP-Server `viper-nats-mcp` (in `viper` eingebaut, per SHA-256 geprüft) auf jedem Rechner einer NATS-Gruppe und trägt ihn bei Claude Code ein: Werkzeuge zum Auflisten der Rechner, Senden, Fragen und Antworten (mit `NATS_OBJECTS` auch zum Senden und Holen von Dateien: der Parameter `attachment` und das Werkzeug `fetch`). In der Gruppe ist nichts privat, und Text anderer Agenten ist nicht vertrauenswürdig: Lesen Sie zuerst die Warnungen im Handbuch. |
| GitHub | `VIPER_GH_TOKEN` | GitHub-PAT, am besten fein granular pro Rechner mit Contents und Pull requests: Read and write (ein für das lokale `gh` exportiertes `GH_TOKEN` wird bewusst nicht verwendet). Auf dem Server ist die GitHub-CLI `gh` angemeldet, und `git` pusht über HTTPS. Der Agent kann so auch Pull Requests anlegen. |
| Claude-Abo | `VIPER_CLAUDE_TOKEN` | Langlebiges Token Ihres Claude-Abos aus `claude setup-token`. Claude Code ist auf dem Server angemeldet, ohne `/login` nach jedem neuen Server. |
| Anderes Modell | `VIPER_ANTHROPIC_BASE_URL`, `VIPER_ANTHROPIC_AUTH_TOKEN`, `VIPER_CLAUDE_MODEL` | Richtet Claude Code auf dem Server auf eine Anthropic-kompatible Schnittstelle, etwa Ollamas Cloud (`https://ollama.com`) oder einen eigenen vLLM-Server. Der Preflight testet Schlüssel und Modell mit einer kleinen Anfrage. |
| Docker | immer | Auf einer VM kommen Engine, Buildx und Compose aus Dockers eigenem apt-Repository und sind damit aktuell. In einem Pod oder Container steckt der Client im Image, und der Daemon ist ein privilegierter Sidecar (oder ein äußerer, oder keiner). |
| Git-Autor | `VIPER_GIT_USER_NAME`, `VIPER_GIT_USER_EMAIL` | Autor der Commits auf dem Server; mit `VIPER_GH_TOKEN` und ohne Wert vom GitHub-Konto (Name und noreply-Adresse). |
| code-server (optional, VMs) | `VIPER_CODE_SERVER=1`, `VIPER_CODE_SERVER_PASSWORD` | Installiert `code-server`, VS Code im Browser, das nur auf `127.0.0.1` lauscht. Zugriff über einen SSH-Tunnel (nützlich auf dem iPad). |
| Swap (optional, VMs) | `VIPER_SWAP` | Legt eine Swap-Datei an, als Faktor vom RAM des Servers (`1` = so viel wie RAM, `0.5` = die Hälfte) oder als Größe (`4G`); standardmäßig aus. Sie fängt Speicherspitzen (`docker build`, `npm install`) ab, statt dass der OOM-Killer zuschlägt. |
| Homebrew | `VIPER_HOMEBREW=0`, `VIPER_BREW_TAPS`, `VIPER_BREW_TRUST`, `VIPER_BREW_PACKAGES`, `VIPER_BREWFILE=1` | `brew` wird auf jedem neuen Server installiert und ist in allen Shells verfügbar (`VIPER_HOMEBREW=0` lässt es weg). Werkzeuge kommen aus den drei Listen (Tap, Trust, Installation, in dieser Reihenfolge) oder, mit `VIPER_BREWFILE=1`, aus einer `Brewfile` im Repository. |
| Befehle nach dem Clone | `VIPER_POST_CLONE` | Shell-Befehle, die auf dem Server im geklonten Repository laufen, nach dem Clone und nach Homebrew (Login-Shell als `builder`, Abbruch beim ersten Fehler, einmalig direkt nach dem Clone; nach einem Fehler versucht es das nächste `viper up` erneut). `VIPER_POST_CLONE_ON_ERROR=retry` (Standard), `ignore` oder `abort` bestimmt, was ein Fehler bewirkt. Log: `~/.config/viper/post-clone.log`. |
| Servertyp suchen | `viper find --cpu N --ram GB --disk GB` | Sucht die günstigsten Servertypen mit mindestens so viel Ausstattung bei Hetzner, AWS, Azure und Google Cloud und zeigt sie in **einer Tabelle auf einer Basis**: in Euro (US-Dollar mit dem Kurs der Europäischen Zentralbank), mit demselben Mehrwertsteuersatz für alle (`--vat`), nach Preis sortiert, mit der Systemplatte im Preis und den Einstellungen zum Übernehmen. Kein Anbieter braucht ein Konto: Die öffentlichen Preislisten werden einmal am Tag gelesen und in `~/.cache/viper` gemerkt (ein Hetzner-Token oder ein Google-Projekt wird, falls gesetzt, zuerst genutzt und gibt die genauen Preise Ihres Projekts). Die Gebühr für die öffentliche IPv4-Adresse steckt in den Preisen. Nur lesend. |
| Sicher löschen | `viper down <name>` | Prüft den Git-Stand aller Repositories und Worktrees im Arbeitsverzeichnis, im Home- und in den Temp-Verzeichnissen (uncommittete Änderungen, Commits auf keinem Remote auf allen Branches, Stash-Einträge), meldet Einträge auf oberster Ebene des Arbeitsverzeichnisses, die zu keinem Repository gehören (Dateien außerhalb von Repositories an anderen Orten prüft es nicht), listet ignorierte Dateien auf und fragt bei ungesicherter Arbeit zusätzlich nach `DISCARD`. |

Die vollständige Anleitung mit allen Aufgaben, Einstellungen und der Fehlerbehebung steht im [Benutzerhandbuch](docs/user/handbuch.md). Für den ersten echten Lauf beginnen Sie dort mit dem Abschnitt „Erster Testlauf mit einem kleinen Server“ (Servertyp `cpx02`, wenige Cent pro Stunde).

## Warum Hetzner Viper?

Ein Code-Agent wie Claude Code soll auf einem Rechner arbeiten, der nicht der eigene Laptop ist: mit viel Leistung, isoliert von den eigenen Daten und Zugängen, dauerhaft erreichbar per tmux und vom iPad bedienbar. Ein Dauerbetrieb lohnt sich dafür nicht. Von Hand sind Server, Firewall, DNS, SSH-Härtung und Repository-Setup bei jedem Start mühsam und fehleranfällig. `viper` macht daraus einen Befehl zum Starten und einen zum Löschen.

## Kerngedanke

Rechner sind Wegwerfware: Alles, was zählt, liegt im Git-Repository. Deshalb hat eine VM bewusst keinen persistenten Datenträger (ein Pod hat Volumes nur, damit er überlebt, wenn sein Cluster ihn ersetzt), und `viper down` schützt vor dem einzigen Risiko, das daraus folgt, nämlich vor ungepushter Arbeit.

## Was macht es vertrauenswürdig?

- **Tests:** `make check` (gofmt, vet, golangci-lint und über 700 Tests, im Devcontainer; CI bei jedem Push; `make help` zeigt die Ziele, `make build` baut `dist/viper`, `make dist-docker` die Release-Dateien ohne Go-Installation). Sie decken Einrichtung, Bereitschaftsprüfung, Mehrrechner-Betrieb, Git-Clone, Firewall- und DNS-Schutz, die Sicherheitsabfragen von `viper down`, den Abbruch mit Ctrl-C und den Parser für `.env.local` (verglichen mit echtem Bash) ab. Die erzeugten cloud-init-User-Data werden mit Referenzdateien verglichen und als YAML gelesen.
- **Schutz fremder Ressourcen:** `viper` ändert und löscht nur DNS-Einträge, die es selbst angelegt hat.
- **Echte Läufe:** Die End-to-End-Tests (Build-Tag `e2e`) richten einen Rechner in einem echten AWS-Konto ein und löschen ihn wieder (`viper up` und `viper down`, x86 und Arm, ohne Cloudflare). NATS-Gruppen und `viper nats` sind bei Hetzner gelaufen, Pods und NATS-Gruppen aus Pods in einem k3d-Cluster, und das Image der Pods hat einen eigenen Test (`make image-test`). Architektur und Tests beschreibt [`docs/maintainer/architektur.md`](docs/maintainer/architektur.md).
- **Handbuch:** [`docs/user/handbuch.md`](docs/user/handbuch.md) mit Versions- und Änderungshistorie.
- **Releases:** Versionen stehen als Tags auf der [Releases-Seite](https://github.com/pt9912/hetzner-viper/releases) mit den `viper`-Binaries und Prüfsummen; zum Erstellen siehe [`docs/maintainer/releasing.md`](docs/maintainer/releasing.md). Zum Entwickeln (Devcontainer, Gates) siehe [`docs/maintainer/developer.md`](docs/maintainer/developer.md).

## Sicherheit und Grenzen

- SSH nur mit Public-Key (kein Passwort, kein Root-Login). Standardmäßig ist Port 22 aus dem ganzen Internet offen. Schränken Sie `SSH_ALLOWED_CIDRS` ein, wenn Sie nur von festen Netzen arbeiten.
- Auf einer VM hat der Benutzer `builder` sudo ohne Passwort und Docker-Zugriff, das entspricht Root. Nutzen Sie nur vertrauenswürdige Repositories. Ein Pod läuft als `builder` ohne root und ohne sudo; sein Docker-Daemon ist standardmäßig ein privilegierter Container, der bei einem Einbruch Root auf dem Knoten bedeutet: Nutzen Sie ihn in k3d oder einem eigenen Cluster, nicht in einem geteilten.
- Serverseitig wird ein CA-signiertes SSH-Host-Zertifikat verwendet (sieben Tage gültig, keine automatische Erneuerung). Der private Host-Key wird dafür in den User-Data des Cloud-Anbieters (Hetzner, EC2) übertragen und ist dort für Administratoren des Projekts und für Prozesse auf dem Server lesbar. Der CA-Schlüssel bleibt lokal. Der einrichtende Rechner hinterlegt den Host-Schlüssel jedes Servers und vertraut nur diesem. Ein abgeflossener Schlüssel eines früheren Servers wird so abgelehnt, und die Verbindung funktioniert auch nach Ablauf des Zertifikats.
- Der Login-Schlüssel hat keine Passphrase.
- **Alles auf dem Server geht beim Löschen verloren** (bei einem Pod mit seinen Volumes), auch eine Claude-Anmeldung per `/login` (mit `VIPER_CLAUDE_TOKEN` ist jeder neue Server automatisch wieder angemeldet).
- Die SSH-Konfiguration jedes Rechners leitet Ihren ssh-agent und X11 nie an den Server weiter, auch wenn Ihre eigene `~/.ssh/config` das tut.
- `viper ui` lauscht nur auf `127.0.0.1`, antwortet nur unter dieser Adresse, gibt gegen einen Schlüssel, der einmal gilt, ein Sitzungs-Cookie aus und ersetzt die bekannten Zugangsdaten in seinen Ausgaben durch `[hidden]`. Es führt dieselben Befehle aus wie das Terminal und kann also Server anlegen und löschen: Starten Sie es nur auf einem Rechner, dem Sie vertrauen.
- `viper` legt kostenpflichtige Ressourcen an. Legen Sie API-Tokens nie in Git ab.
- Nutzen Sie ein eigenes Projekt oder Konto beim Cloud-Anbieter und probieren Sie neue Einstellungen zuerst mit `viper preflight` und einem kleinen Server aus.

## Voraussetzungen

Linux, macOS oder Windows (teilweise getestet; WSL ist zuverlässiger, siehe Handbuch), das Binary `viper` und ein OpenSSH-Client. VS Code Remote-SSH nutzt den lokalen OpenSSH-Client; ohne VS Code nutzen Sie `viper ssh`. Dazu ein Konto bei einem Cloud-Anbieter (ein Hetzner-Cloud-API-Token mit Lesen und Schreiben oder, mit `PROVIDER=aws`, eine AWS-Anmeldung per `aws login`; Google Cloud und Azure beschreibt das Handbuch) oder ein Kubernetes-Cluster mit einem Kontext in Ihrer `kubeconfig` (`PROVIDER=kubernetes`, Docker zum Bauen des Images; k3d genügt) und, für den DNS-Namen, ein Cloudflare-Token mit **Zone DNS Edit/Read** samt Zone-ID (mit `DNS_PROVIDER=none` nicht nötig).
